# Topic: Basic Types

## Objective
Know the scalar data types CQL provides and which ones to use for common column types.

## Why This Matters
Picking the right type matters more in Cassandra than in a relational database because you can't easily change it later. Getting the basics right upfront — especially around numbers and time — saves painful rewrites. Cassandra also has specialized types (collections, static columns, counters), but those depend on concepts we haven't covered yet. For now, focus on the scalar types you'll reach for on almost every column.

---

## Concept

These are the everyday types you'll use for columns.

| Type | Description |
|------|-------------|
| `text` / `varchar` | UTF-8 encoded string (use `text`) |
| `ascii` | ASCII-only string |
| `int` | 32-bit signed integer |
| `bigint` | 64-bit signed integer |
| `smallint` | 16-bit signed integer |
| `tinyint` | 8-bit signed integer |
| `varint` | Arbitrary-precision integer |
| `float` | 32-bit IEEE floating point |
| `double` | 64-bit IEEE floating point |
| `decimal` | Variable-precision decimal (use for money) |
| `boolean` | `true` or `false` |
| `uuid` | UUID (any version) |
| `timeuuid` | Version 1 UUID (time-ordered, guaranteed unique) |
| `timestamp` | Date and time, millisecond precision |
| `date` | Date only (no time) |
| `time` | Time only (nanosecond precision) |
| `duration` | A time span (months, days, nanoseconds) |
| `inet` | IPv4 or IPv6 address |
| `blob` | Arbitrary bytes — use sparingly |
| `vector<float, N>` | Fixed-length float vector (Cassandra 5.0+, used for vector search) |

**Notes:**
- Prefer `text` over `varchar`; they're identical.
- Use `decimal` for currency, never `float` or `double`.
- Prefer `timeuuid` over `timestamp` when you need a time-ordered unique identifier — the reason for this will be more apparent when we get into clustering columns later in this training.
- Later, once we've covered clustering columns, we'll look at the more advanced types: collections, static columns, and counters.

## Examples

### A table using common scalar types
```sql
CREATE TABLE users (
    user_id uuid PRIMARY KEY,
    email text,
    age int,
    balance decimal,
    created_at timestamp,
    is_active boolean,
    last_login_ip inet
);
```

## Pulse Check

> You're storing account balances in dollars and cents. A colleague suggests using `double` for the `balance` column.
>
> **Is that a good idea? What would you recommend instead?**

*(Expected answer: No — `double` is a floating-point type and introduces rounding errors that are unacceptable for money. Use `decimal` for currency values.)*

> You need to record the time at which each event happened with high precision, and every event also needs its own unique identifier. Two colleagues suggest different options: `timestamp` or `timeuuid`.
>
> **Which should you choose, and why?**

*(Expected answer: `timeuuid`. `timestamp` has only millisecond precision, so two events in the same millisecond would collide on identity. `timeuuid` is time-ordered and guaranteed unique, so it gives you both the "when" and a distinct identifier in a single value.)*

> A colleague is storing user IDs — which are UUIDs generated by the application — as `text` in a Cassandra table, because "they're strings in our API anyway." You're reviewing the schema.
>
> **Is there a better type, and why does it matter?**

*(Expected answer: `uuid` (or `timeuuid` if you need time ordering). Storing UUIDs as text wastes space — a UUID is 16 bytes, but its text representation is 36 characters. Cassandra's `uuid` type is more compact and validates format on insert. Use the dedicated type whenever possible.)*
